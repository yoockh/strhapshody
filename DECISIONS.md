## ADR-0001: Web app (Vite+TS) shell, not Tauri/Electron, for MVP

**Context:** PRD §4 recommends a browser web app (no installer, webcam/hand-tracking/audio all
browser-native) but mentions a Tauri/Electron desktop wrapper could be added "later". Yaya
asked for Rust "if possible" but left the final call to the builder.

**Constraints found on this machine:** no `cargo`/`rustc` installed, no `sudo` without a
password prompt, no `webkit2gtk-4.1`/`libappindicator-gtk3` (required for Tauri on Linux) —
installing them needs a manual `sudo pacman -S ...` only Yaya can run. Home internet is slow
(~30-70 KB/s), so large toolchain downloads are a real risk to an unattended long-running build.

**Decision:** Ship MVP as a pure browser web app (Vite + TypeScript), matching the PRD's own
primary recommendation. Use `rustup` (no sudo required, installs to `~/.cargo`/`~/.rustup`) to
get a Rust toolchain for a `wasm-pack`-built WASM engine (`engine/`) that implements the actual
deterministic game logic (hex math, gesture classification, strum detection, power chord math,
distortion curves). This gets genuine, load-bearing Rust into the project — not a toy — while
avoiding the sudo-gated, slow-to-install Tauri system dependencies. Tauri packaging is deferred
to Post-MVP task P.1, to be done once Yaya runs one `pacman` command herself.

**Consequences:** the app runs via `npm run dev` in Chrome/Edge, not as a standalone desktop
binary, until P.1 happens. This matches the PRD's stated MVP bar ("runs on laptop-class
Chrome/Edge/Safari") exactly, so it's not a scope cut, just a sequencing choice.

## ADR-0002: Rust lives only where it doesn't need a camera or a human

**Context:** Hand tracking (MediaPipe) and raw audio I/O (Web Audio API) are both solved,
battle-tested, free, in-browser. Reimplementing either in Rust would mean either FFI bindings
to MediaPipe (fragile, not really "using Rust" in a meaningful way) or training/porting hand
landmark models from scratch (unreasonable scope for this project).

**Decision:** Rust/WASM owns exactly the logic that is pure-function and camera/mic-free: hex
geometry + hysteresis, finger-count gesture classification from landmark coordinates, strum
crossing/direction/velocity math, power chord strip math, One Euro filter smoothing, and
waveshaper curve generation. Everything that needs a live camera frame or live audio hardware
stays in JS/WASM-MediaPipe/Web Audio, where it's proven to work. Why this split matters for a
long-running unattended agent: the Rust layer is 100% unit-testable with synthetic inputs via
`cargo test`, with zero human or camera in the loop — exactly what an agent working alone needs
to self-verify correctness.

## ADR-0003: Open questions from PRD §15 resolved without asking

No further input was available (Yaya explicitly asked for a finished product, not a Q&A). All
five open questions were resolved by keeping the PRD's own stated defaults/assumptions:

1. Power chord strings: "top two strings" = lowest-pitched pair (6th + 5th, low E + A) as the
   default/upper-half mapping, per PRD §7 — this is what real power chords use.
2. Hex layout: circle-of-fifths as specified in PRD §6.1, with layout configurable later
   (Phase 6 settings can expose alternate orderings as a stretch, not required for MVP).
3. Minor chords: finger-count gestures as specified in PRD §6.2 (index = major, index+middle =
   minor) — no evidence it's uncomfortable, and changing it would mean redesigning the whole
   gesture vocabulary with no input to redesign it against.
4. Target laptop: unknown, so performance targets from PRD §10 are treated as the target
   (30-60 FPS tracking, <100ms strum latency) rather than tuning for a specific machine.
5. Who builds it: an autonomous coding agent (Claude Code CLI), orchestrated long-running,
   following this file tree. Noted here since the PRD phrased this as a question about "your
   friend".

## ADR-0004: WASM engine built as a `--target web` module, verified by a node round-trip

**Context:** task 0.2 needs to prove the Rust→WASM→TS pipeline works. wasm-pack can emit several
targets (`bundler`, `web`, `nodejs`, `no-modules`). The frontend is Vite+ESM running in the
browser, and later phases will have the browser frontend `import` engine functions directly.

**Decision:** build the engine with `wasm-pack build engine --target web --out-dir pkg`. The
`web` target emits a browser-native ES module (`engine/pkg/engine.js` + `engine_bg.wasm`) whose
default export is an async initializer and which also exposes a synchronous `initSync`. The wasm
bytes are supplied explicitly (browser: fetched by Vite; tests: read from disk) rather than
bundler-magic'd, so there is no hard dependency on a wasm bundler plugin. `engine/pkg/` stays
gitignored — it is a build artifact regenerated by `npm run build:engine`.

The task-0.2 round-trip is a standalone `node:assert` script (`scripts/engine-roundtrip.ts`, run
via `npm run roundtrip:engine`), executed by Node's built-in TypeScript type-stripping, **not** a
vitest test. Rationale: the vitest harness is task 0.3; keeping 0.2 self-contained means the WASM
pipeline is provable before the frontend test runner exists. `scripts/` is outside the frontend
`tsconfig` `include`, so it never interferes with `npm run build`/`typecheck`.

**Consequences:** `wasm-pack` must be on `PATH` for `build:engine` (it is, via `~/.cargo/bin`).
Future frontend code initializes the engine once at startup (`await init()` with the wasm URL)
before calling exported functions. If a later Vite-integration task prefers the `bundler` target,
supersede this ADR rather than editing it.

## ADR-0005: MediaPipe runtime assets (wasm fileset + model) loaded from CDN, not vendored

**Context:** task 1.1 integrates `@mediapipe/tasks-vision` HandLandmarker. The npm package ships
the JS loader + TypeScript types, but the actual vision WASM runtime
(`vision_wasm_internal.{js,wasm}`) and the hand-landmark model (`hand_landmarker.task`, several
MB) are *not* in the package — they must be supplied at runtime via `FilesetResolver.forVisionTasks(basePath)`
and `baseOptions.modelAssetPath`.

**Decision:** load both from their canonical CDNs at runtime — the wasm fileset from jsDelivr,
pinned to the installed package version (`@mediapipe/tasks-vision@0.10.35/wasm`), and the model
from Google's `storage.googleapis.com/mediapipe-models/...` path. This matches MediaPipe's
documented web setup. Rationale over vendoring: (a) home internet is slow (~30-70 KB/s, see
ADR-0001) so fetching + committing multi-MB binaries now is costly and bloats the repo; (b) these
assets only load in a real browser with a camera, which this execution environment doesn't have,
so they can't be exercised here regardless of where they live; (c) the URLs are version-pinned so
the loader and binaries stay in sync.

**Consequences:** the app needs network access on first run to fetch the wasm + model (they're
then HTTP-cached by the browser). Hand-tracking init is wrapped in a `.catch` in `main.ts`: if the
assets can't load (offline), the app keeps showing the mirrored feed without a landmark overlay
rather than failing. If an offline/air-gapped build is ever required, supersede this ADR with a
vendor-and-serve-locally approach (download into `public/`, point `basePath`/`modelAssetPath` at
same-origin URLs) — the `handtracking.ts` constants are the only thing that changes.

**Testability note (ADR-0002 split):** the WASM-bound tracker (`handtracking.ts`) is deliberately
thin and unit-test-free; all the load-bearing, verifiable logic — mapping normalized landmarks
through the cover-crop + mirror transform, and the hand-skeleton connection topology — lives in
the pure `handoverlay.ts` module and is covered by `cargo`-style synthetic unit tests under vitest.

## ADR-0006: One Euro smoothing is a per-scalar stateful filter, timestamps in seconds

**Context:** task 1.3 is the first real engine logic module — One Euro filter smoothing for the
noisy hand-landmark signal. Two API-shape questions had to be settled: (a) does one filter
instance smooth a whole landmark (a vector) or a single scalar; (b) what units/contract do
timestamps follow, given MediaPipe hands us `performance.now()` milliseconds per frame.

**Decision:** the engine exports `OneEuroFilter` as a **stateful** `#[wasm_bindgen]` struct
(`new OneEuroFilter(minCutoff, beta, dCutoff)`, `.filter(x, timestamp)`, `.reset()`) that smooths
**one scalar stream**. The frontend creates one instance per coordinate it wants smoothed (e.g. an
x and a y for a palm-centre point). Rationale: scalar is the simplest fully-testable primitive, it
composes trivially into any dimensionality, and it avoids baking a fixed landmark layout or an
array-marshalling convention into the wasm boundary this early. The pure core (`OneEuro`, no
wasm-bindgen) is separate from the exported wrapper so it's reusable and testable from native Rust.

Timestamps are **seconds** (the frontend divides `performance.now()` by 1000 before calling).
Seconds make the cutoff-frequency math read in natural Hz units. The filter requires non-decreasing
timestamps; a non-advancing/first/backwards timestamp falls back to a nominal 60 Hz period instead
of dividing by zero. Non-finite samples and non-positive/NaN config are sanitized so live garbage
can never produce NaN output — important for an unattended agent feeding it real tracker data.

**Consequences:** `reset()` must be called when tracking is lost so the next sample re-seeds
instead of lerping from a stale position (the UI integration in a later phase will wire that to the
hand-presence signal). If a future phase needs to smooth many coordinates cheaply in one call, add
a vector/batch export then rather than reshaping this scalar one — this ADR isn't superseded by
adding a complementary batch API, only by changing the scalar contract itself.

## ADR-0007: Strum detection is an event stream with a half-open crossing interval

**Context:** task 2.2 is the `strum` engine module. PRD §8 wants each virtual string to fire "at
the moment the hand crosses its line" (the rake), with up/down direction and a speed that drives
loudness. Two contract questions had to be settled: (a) what shape the module exposes to the audio
layer (2.4) and the power-mode restriction (4.3); (b) how to define a "crossing" so a hand that
comes to rest on a line, or jitters near one, doesn't machine-gun that string.

**Decision:** `StrumDetector` is a **stateful** detector fed one hand-point `(y, timestamp)` sample
at a time via `.push()`, returning the string crossings for *that step only* as a `Vec<StrumEvent>`
(`{ string_index, direction: StrumDirection, velocity }`), in rake order (top→bottom for a
downstroke, bottom→top for an upstroke). The pure core `StrumCore` is wasm-free and holds all the
tested logic; the `#[wasm_bindgen]` wrapper is thin, matching the ADR-0002 / ADR-0006 split. Returning
`Vec<StrumEvent>` across the boundary is supported natively by wasm-bindgen 0.2.130 and emits a clean
`push(y, timestamp): StrumEvent[]` TS signature, so the frontend gets a real array of objects.

A line at `s` is crossed on a step `last_y → y` using a **half-open** interval: moving down,
`last_y < s <= y`; moving up, `y <= s < last_y`. This fires a line exactly once per actual pass and
guarantees that resting on a line, or leaving it, never re-fires it (a near-miss or wobble that never
reaches the line fires nothing). Velocity is `|Δy|/Δt` in **px/second**; a non-advancing timestamp
falls back to a nominal 60 Hz period so it's always finite and ≥ 0. String y positions are sorted
ascending and NaNs dropped at construction, so `string_index` is stable (0 = topmost = low E per
`strings.ts`) regardless of caller order.

**Consequences:** the caller must call `.reset()` when tracking is lost or the hand leaves the strum
zone, otherwise a large jump back in would register as one giant strum across every line (there is a
regression test for exactly this). The audio layer (2.4) consumes the returned events directly as
voice triggers. If a future phase needs sub-frame crossing *timestamps* per string (for even tighter
rake timing than one velocity-per-step), extend `StrumEvent` with a per-crossing time rather than
reshaping the push contract — this ADR is superseded only by changing the `(y,ts) → events` shape or
the crossing-interval convention itself.

## ADR-0008: Landmark sets cross the WASM boundary as a flat interleaved x,y slice; gestures use scale-invariant distance ratios

**Context:** task 2.3 (`gesture` module, palm-mute + fist-stop) is the first engine module that
needs a whole hand's 21 MediaPipe landmarks, not just a scalar (smoothing) or a single point
(strum). Two contract questions had to be settled, and both will be inherited by the next
landmark consumer (task 3.3 finger-count classification, and later power-strip/hex cursor work):
(a) how a landmark set is marshalled across the JS↔WASM boundary; (b) how "extended vs. curled"
is judged robustly without knowing the hand's size, position or rotation in frame.

**Decision:**
1. **Boundary shape** — a hand is passed as a flat `&[f64]` of **interleaved `x, y` pairs**,
   length 42 (`[x0,y0, x1,y1, …, x20,y20]`), i.e. a `Float64Array` from JS. Only image-plane
   `x, y` are used; MediaPipe's `z` is relative/noisier and the palm-vs-fist distinction is
   already unambiguous in 2D. A flat slice (vs. an array of structs across the boundary) is the
   cheapest, most portable marshalling and matches the scalar-first spirit of ADR-0006/0007.
   Wrong length or any non-finite coord is treated as "no hand" → `Neutral`, never a panic.
2. **Geometry** — a finger's extension is a **straightness ratio**
   `dist(MCP,TIP) / (dist(MCP,PIP)+dist(PIP,DIP)+dist(DIP,TIP))`: ~1 when straight, →0 when
   curled back toward the palm. Being a ratio of distances it is invariant to translation, scale
   and rotation (regression-tested), so it needs no hand-size calibration. Extended at
   `ratio ≥ 0.80`, curled at `ratio ≤ 0.60`, with the gap a deliberate dead zone so a half-open
   hand reads `Neutral` instead of flickering. The thumb is excluded (different, noisier
   geometry; the four fingers alone disambiguate flat-palm from fist). `OpenPalm` = all four
   extended, `Fist` = all four curled.
3. **Debounce** — per-frame classification is wrapped in a stateful `GestureCore` that requires a
   new shape to persist `hold_frames` (default 3) consecutive frames before committing, matching
   the "stateful detector + `reset()` on tracking loss" pattern of strum/smoothing.

**Consequences:** the frontend flattens each hand's landmarks to a 42-element `Float64Array`
before calling `GestureDetector.update()` / `classifyHandShape()`, and calls `.reset()` when the
right hand is lost (wired with the audio work in 2.4). The exact thresholds and `hold_frames` are
feel-tunable (Phase 6.2 sensitivity sliders, Phase 7.3 manual checklist) — changing their *values*
does not supersede this ADR; only changing the interleaved-x,y boundary shape or the
straightness-ratio metric itself would. If a future module needs `z`, add a parallel 63-element
entry point rather than redefining the 42-element one.

## ADR-0009: Web Audio skeleton — pure note math in TS, thin voice wrapper; test chord = open strings; first frontend→WASM init

**Context:** task 2.4 is the first task that (a) makes sound and (b) actually wires the browser
frontend into the WASM engine (the `strum` detector from 2.2). Several contract questions had to
be settled: where the audio logic splits between testable-pure and DOM-bound; what the "single
hardcoded test chord" is; how strum velocity maps to loudness; how the right hand's position feeds
the strum detector; and how the `wasm-pack --target web` engine is initialized in the browser.

**Decisions:**
1. **Where the ADR-0002 split falls for audio.** Note→frequency math (`notes.ts`:
   scientific-pitch-notation parsing, equal-temperament `midiToFrequency`, the test-chord
   frequency table) and the strum-velocity→voice-gain mapping (`velocityToGain` in `audio.ts`) are
   pure and unit-tested. Everything that needs a live `AudioContext` — oscillators, envelopes,
   per-string voice allocation, resume-on-gesture — is a thin wrapper (`createAudioEngine`) not
   unit-tested here (no audio hardware in this env), exercised by the Playwright e2e suite (7.1)
   and a human. `audio.ts` touches no Web-Audio symbol at module load, so importing it under node
   to test `velocityToGain` is safe.
2. **Test chord = the six open strings** (E2 A2 D3 G3 B3 E4), matching `STRING_NOTE_NAMES` top→
   bottom. Strummed together they ring as a real open-position voicing, so the skeleton sounds
   musical, not like a test tone, without pre-empting the Phase-3 chord tables (which will call
   `setChord()` to replace the note set).
3. **Pluck = placeholder triangle oscillator** through a per-voice gain with a fast attack and a
   ~1.4 s exponential decay, summed on a master bus. Six voice *slots* (one per string); re-plucking
   a string fast-fades and replaces its previous voice, like a real string that can only ring one
   note at a time. `stopAll()` exists for the fist-stop gesture (2.3) to use later. The timbre is
   explicitly throwaway — Phase 5 replaces it with Karplus-Strong (5.1) and the waveshaper electric
   voice (5.2). `velocityToGain` maps |Δy|/Δt (px/s) linearly to `[0.08, 1.0]` up to a 3000 px/s
   reference, then saturates, so even a gentle strum is audible and a hard one doesn't clip harder.
4. **Strum-point source.** The detector is fed the strum hand's palm centre (mean of wrist +
   middle-MCP, the same steady point `handedness.representativeX` uses), mapped to canvas y through
   the exact `landmarkToCanvas` cover-crop+mirror transform the overlay uses, so crossings align
   with the drawn string lines. The detector is rebuilt when the string-line y positions change
   (resize) and `.reset()` every frame the strum hand is absent, so a hand re-entering frame can't
   register as one whole-zone strum (the ADR-0007 hazard). Timestamps are `performance.now()/1000`
   (seconds), matching the smoothing/strum seconds convention.
5. **Engine init (first frontend→WASM integration).** The `wasm-pack --target web` module's default
   export is an async initializer that must run once before any export is constructed (ADR-0004).
   `engine.ts` wraps it in an idempotent `initEngine()` promise and re-exports `StrumDetector` /
   `StrumEvent` / `StrumDirection`, so callers don't re-implement the init dance. Vite bundles
   `engine_bg.wasm` as an asset automatically (confirmed: `npm run build` emits
   `dist/assets/engine_bg-*.wasm`). This supersedes nothing in ADR-0004 — it's the "future frontend
   code initializes the engine once at startup" that ADR-0004 anticipated, now realized.

**Consequences:** the AudioContext starts suspended (browser autoplay policy) and is resumed on the
first pointer/key event via a one-shot listener; nothing sounds before a user gesture, which is
correct and also means audio can't be confirmed in this headless env. `StrumEvent` objects returned
across the boundary are `.free()`d after their fields are read, to avoid leaking wasm memory in the
per-frame hot path. Changing the pluck timbre, envelope times, `velocityToGain` constants, or the
test-chord notes does not supersede this ADR; only changing the pure/DOM split, the engine-init
contract, or the strum-point mapping would.

## ADR-0010: Hex map is flat-top hexagons, nearest-centre Voronoi containment, inflate/deflate hysteresis

**Context:** task 3.1 is the `hexmap` engine module (PRD §6.1): a 7-cell "flower" (centre C; ring
clockwise from top G, D, A, E, B, F, the circle of fifths), a point-in-hex test for the palm-centre
cursor, and border hysteresis so a cursor on a seam doesn't flicker between two chords. Three
contract questions had to be settled, and task 3.2 (hex UI), 3.3/3.4 (gesture + chord-change rule)
inherit them: (a) hex orientation; (b) how containment is decided; (c) how hysteresis is shaped.

**Decision:**
1. **Flat-top hexagons.** A flat-top hex (flat edge on top) is the only orientation with a neighbour
   *directly above* the centre, which is what "G at the top of the ring" requires. Ring cells sit at
   centre-to-centre distance `√3·R` (two apothems) from the centre, at 60° intervals clockwise from
   straight up; in screen coords (y down) the offsets are the table in `hexmap.rs`. Cell index order
   is fixed `[C, G, D, A, E, B, F]` with `CELL_CHORDS` exposed so the UI/audio layers share one
   mapping rather than re-deriving letters.
2. **Nearest-centre + exact containment.** A regular hex tiling is the Voronoi diagram of its
   centres, so the cell a point falls in is the one with the nearest centre — confirmed by an exact
   flat-top-hexagon inequality (`|dy| ≤ √3/2·r` and `√3·|dx|+|dy| ≤ √3·r`). The confirm step is what
   makes a point just *outside* the flower (whose outer edges have no neighbour) read as "no cell"
   rather than snapping to the nearest outer hex. `raw_cell` is the stateless version; `update` adds
   hysteresis.
3. **Inflate/deflate hysteresis.** The selector is stateful (like strum/gesture/smoothing): it holds
   the current cell while the cursor stays inside that cell *inflated* to `R+margin`, and only adopts
   a different cell once the cursor is *deep* inside it (inside it *deflated* to `R−margin`) or has
   left the inflated current cell entirely. This is a dead band of total width `√3·margin` around
   every seam — the PRD's "must move a little past the border to switch". `margin` is clamped to
   `[0, 0.49·R]`; radius floored positive; non-finite config sanitised; a non-finite cursor sample
   *keeps* the held cell (one garbage frame must not drop the chord).

Boundary shape: the `#[wasm_bindgen] HexMap` wrapper returns cell indices as `i32` with `-1` ==
"no cell" (no Option shim needed in TS), plus `centerX/centerY/radius/cellCount/cellChord` getters
for the task-3.2 renderer. The pure `HexCore` holds all tested logic, matching the ADR-0002 split.
Cursor coords are canvas pixels (the frontend will map the smoothed palm centre through the same
cover-crop+mirror transform the overlay/strum point use).

**Consequences:** the frontend creates one `HexMap` sized to the left zone, rebuilds it on
resize/hex-size change, feeds it the smoothed palm centre each frame, and calls `.reset()` when the
left hand is lost. The "chord only changes between strums" rule (task 3.4) sits *above* this module —
`update()` tracks the live hover; 3.4 latches the sounding chord to a strum boundary. Changing the
`margin` default or hex size is feel-tuning (Phase 6.2 sliders), not an ADR change; only changing the
orientation, the containment metric, or the hysteresis scheme would supersede this. Alternate hex
layouts (PRD §6.1 "can be changed in settings", ADR-0003 §2) would re-order `CELL_CHORDS` / the
offset table, not reshape the API.

## ADR-0011: Finger-count quality is a clean-pattern classifier that holds the last quality on an ambiguous/lost hand

**Context:** task 3.3 is the `fingercount` engine module (PRD §6.2): the left hand hovers a hex to
pick the chord *root* while the number of extended fingers sets the chord *quality* (index = major,
index+middle = minor, index+middle+ring = dominant-7th, the latter a stretch goal). It reuses the
exact landmark boundary + straightness metric of the `gesture` module (ADR-0008), so the only new
contract questions are: (a) what finger patterns count as a clean, committed gesture; (b) what a
detector reports before any clear gesture; (c) how an ambiguous or lost-hand frame is treated.

**Decision:**
1. **Clean-pattern classification.** A quality is only recognised for a *contiguous run* of
   clearly-extended fingers starting at the index — index / index+middle / index+middle+ring — with
   **every** finger past the run, **including the pinky**, clearly curled. Any finger in the
   straightness dead zone (ambiguous), the index not extended, a gap (e.g. index+ring, no middle),
   or a raised pinky yields `ChordQuality::Unknown` ("no clear finger-count this frame"). Requiring a
   clean pattern means a half-formed hand never silently flips the sounding quality. The thumb is
   excluded (same noisy-geometry rationale as ADR-0008).
2. **Default = `Major`.** A freshly-created / just-reset detector reports `ChordQuality::Major`
   before any clear gesture — the natural default quality when a hex is first hovered.
3. **`Unknown` *holds*, it does not decay (differs from `gesture.rs`).** Chord quality is a
   *selection* (like the hovered hex cell of ADR-0010), not a momentary modifier like palm-mute. So
   an `Unknown` frame — an ambiguous hand, or a lost hand producing an invalid slice — holds the last
   committed quality; only a *different* clear quality sustained `hold_frames` (default 3) consecutive
   frames replaces it. This mirrors ADR-0010's "non-finite sample keeps the held cell; reset on
   tracking loss" rather than the gesture detector's decay-to-`Neutral`. `reset()` returns to `Major`
   when the chord hand is lost.

Boundary shape (ADR-0008): a hand is a flat 42-value `Float64Array`; the `#[wasm_bindgen]`
`FingerCountDetector` wraps the pure `FingerCountCore` (all tested logic), plus a stateless
`classifyChordQuality()` export and the `ChordQuality` enum. Shared per-finger primitives
(`finger_extended`, `landmarks_valid`, the finger index tables) are reused from `gesture.rs` (made
`pub(crate)`) rather than duplicated.

**Consequences:** task 3.4 (chord-change-only-between-strums) latches this committed quality together
with the hovered hex root to a strum boundary; task 3.5 maps (root, quality) to a fret/note set.
Changing the `hold_frames` default or the `EXTENDED_MIN`/`CURLED_MAX` thresholds (shared with
`gesture`) is feel-tuning (Phase 6.2 sliders / 7.3 checklist), not an ADR change; only changing the
clean-pattern rule, the default quality, or the hold-on-`Unknown` behaviour would supersede this.

## ADR-0012: Chord latch — pending/committed split, commit on strum boundary, committed chord persists

**Context:** task 3.4 is the "chord changes only between strums" rule (PRD §6): a guitarist's chord
doesn't change the instant the fretting hand moves — it changes when the picking hand next strikes.
So the *sounding* chord must update only at a strum boundary, never mid-ring. Three contract
questions had to be settled, and task 3.5 (chord→note-set) inherits them: (a) where this rule's
state lives and how it's shaped; (b) what a strum "boundary" is in the per-frame pipeline; (c) how
transient left-hand loss / off-flower frames are handled so the ringing chord isn't dropped.

**Decision:**
1. **Pure engine module `chordlatch.rs` with a pending/committed split (ADR-0002).** `ChordLatchCore`
   holds a **pending** selection (root cell index `i32` + `ChordQuality`), updated every frame from
   the hovered hex cell (ADR-0010) and the finger-count quality (ADR-0011), and a **committed**
   selection — the sounding chord — that only changes when `commit()` is called. `commit()` copies
   pending→committed and returns whether it actually changed. The `#[wasm_bindgen] ChordLatch`
   wrapper is thin (`setPending(root, quality)`, `commit() -> bool`, `committedRoot`/
   `committedQuality`/`pendingRoot`/`pendingQuality` getters, `reset()`), matching the stateful-
   detector pattern of strum/gesture/hexmap/fingercount. One instance holds the app's sounding chord.
2. **Strum boundary = a crossing frame; commit before the voices fire.** The frontend calls
   `chordLatch.commit()` in `processStrum` whenever the strum detector returns ≥1 `StrumEvent` this
   frame, *before* triggering the pluck voices, so the strum that armed the change also sounds it.
   Committing once per crossing frame is a no-op when the selection hasn't moved, so a multi-frame
   single stroke doesn't matter. "Never mid-ring" is satisfied because `commit()` is the *only* path
   that changes the committed chord — while a chord rings out with no crossing, the left hand can roam
   freely and the sounding chord stays put (regression-tested).
3. **Hold-last / persist rules (mirror ADR-0010/0011).** `set_pending` with a negative root (cursor
   outside the flower) *keeps* the last valid pending root; an `Unknown` quality keeps the last
   pending quality — a transient off-flower / ambiguous frame must not arm a silent "no chord" strum.
   The committed chord **persists** across chord-hand tracking loss: the frontend does NOT reset the
   latch per-frame (unlike the hexmap selector / finger-count detector, which it *does* reset on loss
   for a clean cursor re-entry). `reset()` is a full clear for app-reset/tests only. A brief dropout
   therefore can't drop the ringing chord (regression-tested).

**Consequences:** the status bar's CHORD field now shows the *sounding* (committed) chord — root
letter via `HexMap.cellChord` + a quality suffix (`""`/`m`/`7`) formatted by the pure, unit-tested
`src/chord.ts` (`chordLabel`) — which only changes on a strum; the hovered-but-not-yet-strummed cell
is still shown by the flower's accent, so hover feedback isn't lost. Before the first strum the field
shows an em-dash placeholder. Task 3.5 reads `committedRoot`/`committedQuality` to pick the note set
`setChord()` loads; until then the voices still play the placeholder open-string test chord, so 3.4's
observable effect is the latched status-bar chord. The finger-count detector is now wired into the
live render loop for the first time (`processChord` flattens the chord hand's landmarks to the
42-value `Float64Array` of ADR-0008 and feeds `FingerCountDetector.update`). Changing *when* the
frontend commits (e.g. only on the first crossing of a stroke rather than any crossing frame) or the
chord-label formatting is not an ADR change; only changing the pending/committed split, the
commit-on-boundary contract, or the hold/persist rules would supersede this.

## ADR-0013: Power strip is stateless rectangle geometry — 13 equal fret cells, midline string-pair split, octave two strings below the root

**Context:** task 4.1 is the `powerstrip` engine module (PRD §7). The left hand hovers a horizontal
strip above the hex grid where **x selects the fret (0–12)** and **height selects the string pair**
(upper = 6th+5th, lower = 5th+4th). Several contract questions had to be settled, and tasks 4.2 (strip
UI + Power/Chord mode switch) and 4.3 (restricted strumming + "G5 (fret 3, low E)" display) inherit
them: (a) how x maps to a discrete fret and where the fret markers sit; (b) how the height splits into
the two pairs and which exact string indices each pair drives, including the optional octave; (c)
whether the module is stateful (like hexmap/strum) or stateless; (d) where the note-name math lives.

**Decision:**
1. **13 equal-width fret cells, right edge clamps.** Frets `0..=max_fret` (default 12 per PRD §7) are
   `max_fret + 1` equal cells spanning the strip width; `fret = floor((x−left)/cell_width)`, with the
   inclusive right edge clamped to the top fret rather than overflowing to a phantom cell. x outside the
   strip's horizontal span is "no fret" (`-1` at the boundary). `fret_marker_x(fret)` returns a cell's
   *centre* for the renderer, and every marker round-trips back to its own fret (regression-tested).
   Frets are monotonic in x so "moving right raises the pitch" (PRD §7) holds by construction.
2. **Midline string-pair split; octave is two strings below the root.** The strip's height splits at its
   midline — upper half → `PowerPair::Upper` (root on string 0 = 6th/low E, fifth on 1 = 5th/A), lower
   half → `Lower` (root on 1 = 5th/A, fifth on 2 = 4th/D), using the `strings.ts` index convention
   (0 = low E at top). The exact midline counts as Upper. The **optional octave** is the string two below
   the root (Upper → 2 = 4th/D, Lower → 3 = 3rd/G), i.e. the standard E-shape / A-shape power-chord octave
   that task 4.3 may add as the third strummed string. This realises ADR-0003 §1 (lowest pair is the
   default) concretely.
3. **Stateless, pure (ADR-0002).** Unlike the hexmap selector / strum detector, the strip has **no
   hysteresis and no per-frame state** — it is pure rectangle geometry queried fresh each frame
   (`fret_at_x`, `pair_at_y`, `contains`). The Power/Chord *mode* latch and any dwell/hysteresis on the
   mode boundary belong to the frontend wiring in task 4.2, above this module, not inside it. Edges are
   normalised (any argument order → `left<right`, `top<bottom`), and a degenerate or non-finite rectangle
   is floored to a tiny positive extent so no query divides by zero.
4. **No note names in the engine.** The module emits only the fret *number* and the affected *string
   indices*; turning `(fret, string)` into "G5 (fret 3, low E)" is note math that stays in TypeScript
   alongside `notes.ts`/`chords.ts` (task 4.3), matching where the chord-table note math already lives
   (ADR-0009/3.5). Boundary encoding mirrors `HexMap`: fret as `i32` (`-1` = off-strip), pair as `i32`
   (`-1` none / `0` upper / `1` lower), no Option shim in TS.

**Consequences:** task 4.2 builds a `PowerStrip` sized to a strip rectangle above the hex flower, uses
`contains()` on the smoothed left-palm cursor to switch into Power mode (and back to Chord mode on
leaving), and draws fret markers at `fretMarkerX()`. Task 4.3 reads `fretAtX`/`pairAtY` + the
`rootString`/`fifthString`/`octaveString` indices to restrict the strum voices and format the status-bar
note name. Changing the default `max_fret`, the cell count, or adding mode-boundary hysteresis in the
*frontend* is not an ADR change; only changing the equal-cell fret mapping, the midline split, the
string-index/octave convention, or moving note-name math into the engine would supersede this.

## ADR-0014: Power-mode strum restriction is a note-set property; power chords latch on the strum boundary too

**Context:** task 4.3 makes Power mode actually sound: the right hand should strum only the 2 (optionally
3 with octave) power-chord strings, and the status bar should read e.g. "G5 (fret 3, low E)" (PRD §7).
Questions: (a) where the "only these strings" restriction lives; (b) when a newly hovered power chord
starts sounding; (c) whether the octave is on; (d) what happens to strings left ringing from the previous
voicing.

**Decision:**
1. **Restriction = silent strings in the voicing.** A pure TS module (`src/voicing.ts`) turns the power
   selection into a six-string frequency array with `0` Hz on every string except root / fifth / octave.
   The audio engine already treats a non-positive frequency as "don't sound" (ADR-0009), so the strum
   detector and pluck path stay untouched — no mode branch in the hot path. Pitches are derived as note
   math (root = open string + fret, fifth = +7, octave = +12, each placed on the string index the engine's
   `powerstrip` returned), per ADR-0013 §4; nothing about tuning is hard-coded beyond `OPEN_STRING_MIDI`.
2. **Same strum-boundary rule as chords (ADR-0012).** The hovered power chord is a *pending* selection
   (last valid fret+pair, held through gap/off-strip frames); the engine's note set only changes on a strum
   frame. `selectVoicing(mode, power, chord)` picks the power chord in Power mode, else the latched hex
   chord; the frontend reloads the engine only when the voicing's identity `key` changes (so Power→Chord
   with an unchanged latched chord still swaps the note set back). The latch itself is unchanged and still
   commits on every crossing frame. The strip previews the hovered power chord name before it sounds; the
   status bar shows the *sounding* voicing's label.
3. **Octave on by default** (`POWER_CHORD_OCTAVE = true` in `main.ts`) for a fuller sound; it's the PRD's
   "optional" third string and becomes a Phase 6.2 setting.
4. **`setChord()` damps strings the new voicing doesn't sound**, as a guitarist's fretting hand would —
   otherwise a low E ringing from a G chord would bleed under an A5 or a C (whose low E is muted).

**Consequences:** the status bar's CHORD field now shows the last loaded voicing label (chord or power);
`applyCommittedChord` in `main.ts` is replaced by `applySoundingVoicing`. Changing the octave default or
the label format is not an ADR change; moving the restriction into the strum path or letting a power chord
sound mid-ring would supersede this.

## ADR-0015: Acoustic voice = Karplus-Strong rendered to a buffer in the Rust engine, injected into the audio engine

**Context:** task 5.1 replaces the placeholder triangle-oscillator pluck with a real acoustic guitar voice.
TASKS.md names Karplus-Strong as the pragmatic choice (no sample licensing, testable by inspecting the
output buffer). Questions: (a) where the DSP runs — Rust/WASM, TS, or an AudioWorklet; (b) how it reaches
Web Audio; (c) how per-note parameters are chosen.

**Decision:**
1. **Rust `pluck` module renders a whole note to a `Vec<f32>`** (`renderPluck(freq, sampleRate, duration,
   t60, brightness, seed) → Float32Array`). Extended KS: seeded lowpassed noise burst, two-point-average
   loop filter with loss `ρ = 10^(−3/(t60·f))`, and a first-order allpass for fractional-delay tuning.
   Being a pure function it is `cargo test`-ed on the samples: pitch within 1 cent across E2–E5 (measured
   < 0.11 cent), T60 decay, palm-mute thud, brightness tilt, boundedness, DC, determinism, sanitisation.
   An AudioWorklet was rejected for now: real-time streaming adds a second wasm instance in the worklet
   scope and a message protocol, for no audible gain on a 6-voice instrument; rendering a ≤3.5 s note is
   sub-millisecond in wasm.
2. **Played as an `AudioBufferSourceNode` per pluck**, through the existing per-voice gain → master bus,
   so retrigger/`stopAll`/damping from ADR-0009/0014 work unchanged. The renderer is **injected**
   (`audioEngine.setPluckRenderer(renderPluck)` after `initEngine()`), so `audio.ts` stays wasm-free and
   node-importable, and the instrument is playable before the wasm loads (oscillator fallback, also used
   if a render throws or returns empty).
3. **Per-note parameters are pure TS** (`acousticPluckParams`): T60 ∝ 1/√f clamped to [1.2, 6] s (~5 s on
   low E, ~2.6 s on high e); brightness from strum velocity (harder = brighter); render length capped at
   3.5 s (fade built into the buffer); palm-muted = T60 0.18 s, half brightness. Each pluck gets a new
   seed so repeated strums aren't sample-identical.

**Consequences:** the electric voice (5.2) reuses the same KS source and adds a waveshaper/tone chain after
the voices. Retuning T60/brightness constants is feel-tuning, not an ADR change; moving synthesis into an
AudioWorklet or to samples would supersede this.

## ADR-0016: Electric voice — shared waveshaper chain with drive 0 as "clean", curve from the engine

**Context:** task 5.2 adds an electric clean + distortion voice: a `WaveShaperNode` driven by a Rust curve
generator with a drive parameter, plus a basic tone control. Questions: (a) curve shape; (b) whether clean
and distortion are separate chains; (c) tone control form; (d) keeping loudness sane as drive rises.

**Decision:**
1. **Curve = normalised tanh soft clip** `y = tanh(k·x)/tanh(k)`, `k = 40·drive`, from the new engine module
   `distortion.rs` (`distortionCurve(samples, drive)`). Odd-symmetric (no DC, odd harmonics), monotonic,
   `y(±1) = ±1`, identity at drive 0. Cargo-tested on those properties plus "more drive ⇒ more gain and a
   squarer sine" (crest factor √2 → ~1).
2. **One electric chain for both instruments**: voices → bus → (acoustic send → master) or (electric send
   ×0.3 → WaveShaper 4× oversampled → lowpass tone → compensation gain → master). "Electric Clean" is the
   same chain at drive 0 (shaper curve `null` = pass-through), "Electric Dist" uses the drive (default 0.6).
   Switching crossfades the two sends (10 ms time constant). The curve generator is injected after engine
   init, like the pluck renderer (ADR-0015); before then electric is simply clean. Curves are cached per
   1% of drive.
3. **Tone = 12 dB/oct lowpass**, knob `[0,1]` mapped exponentially to 700 Hz–12 kHz (`toneToCutoff`),
   default 0.65 (~4.4 kHz) to tame the fizz of the saturated highs. Acoustic bypasses it.
4. **Level compensation** `1/(1+12·drive)` on the chain output, tuned by measuring master-bus RMS in
   headless Chromium (6-string strum): acoustic 0.088, clean 0.099, distortion 0.118 — distortion lands a
   little louder, not +7 dB as with a weaker factor. Electric plucks use brighter excitation and longer
   T60 (∝1/√f, 2.5–9 s) than acoustic.

**Consequences:** `AudioEngine` gains `setInstrument / instrument / setDrive / setTone /
setCurveGenerator`; task 5.3 adds the UI toggle and reverb on top. Changing k, the tone range or the
compensation constant is tuning; a separate clean chain, an asymmetric curve, or moving the curve into TS
would supersede this.

## ADR-0017: Sound controls — synthetic reverb IR from the engine, DOM control panel, 1/2/3/I shortcuts

**Context:** task 5.3 adds an instrument toggle (on-screen + keyboard), volume, and a simple reverb with an
amount control. Questions: (a) recorded vs algorithmic reverb, and where it's generated; (b) how the
controls are drawn; (c) which keys, given the task-6.4 keyboard fallback will own A–G, Shift and Space.

**Decision:**
1. **ConvolverNode with an IR synthesised by the engine** (`reverb.rs`, `reverbImpulse(sr, rt60, damping,
   seed)`): 8 ms pre-delay, noise under an e^(−ln1000·t/RT60) envelope, a one-pole lowpass that darkens over
   the tail, normalised to unit energy; stereo = two seeds (cargo-tested correlation < 0.1). No recorded IR
   to license or download (ADR-0001/0005). `convolver.normalize = false` because the IR is already
   unit-energy, so the wet level is predictable. Defaults: RT60 2.2 s, damping 0.6, amount 0.25.
2. **Mix and volume are pure TS:** `reverbMix(a)` → dry `1−0.3a`, wet `0.8a`; `volumeToGain(v) = 0.55·v²`
   (perceptual; default 0.8 ≈ the previous fixed 0.35 master). Graph: instrument routes → mix → (dry, and
   convolver → wet) → master(volume) → destination. IR generator injected after engine init (ADR-0015
   pattern); before that the wet path is silent.
3. **DOM panel, not canvas:** real buttons (`aria-pressed`) and `<input type=range>` sliders, bottom-right,
   so they work with mouse/touch/keyboard and screen readers. Buttons blur after click so Space stays free
   for strumming.
4. **Shortcuts `1`/`2`/`3` (Acoustic / Electric Clean / Electric Dist) and `I` (cycle)**; ignored with
   Ctrl/Meta/Alt and while a slider has focus. Volume/reverb have no shortcuts (sliders only) to keep the
   key map small next to the 6.4 fallback.

**Consequences:** settings persistence (localStorage) is task 6.2's job and will cover these too. Changing
RT60/damping/mix constants is tuning; using a recorded IR or an algorithmic (Freeverb-style) network would
supersede this.

## ADR-0018: Calibration records robust per-hand ranges in normalised coords and fits zones inside their halves

**Context:** task 6.1 — a ~20 s first-run calibration capturing each hand's comfortable range and resizing
the zones to match. Questions: (a) the flow and how ranges are measured robustly; (b) how a range becomes
a zone; (c) persistence and when it runs.

**Decision:**
1. **Timed flow, one hand at a time:** intro 3 s → left 8 s → right 8 s → done 1.5 s (20.5 s). Recording one
   hand per phase means the user can focus, and the left phase isn't polluted by strumming motion. The
   range is the **5th–95th percentile box** of the palm-centre samples (≥ 30 samples, else that hand keeps
   its previous/default zone), so a stray mis-tracked frame can't inflate a zone. A pure
   `CalibrationSession` holds the clock + samples; strumming is paused while it runs and the strum
   detector is reset after (ADR-0007 re-entry hazard).
2. **Range → zone (`calibratedZones`):** pad 15% per side, grow to a minimum (left: 55% × 60% of its half,
   strings: 50% × 45%) around the range centre, and clamp inside **its own half** below the status bar.
   Keeping zones in their halves means role assignment by screen side (ADR handedness/§13) still agrees
   with where the UI is, and the two zones can never overlap. The left zone feeds the existing
   strip+hex layout; the right zone gives the strings' y-span (strum detector) and x-span (drawing).
3. **Stored normalised (0..1, mirrored as seen)** under `strhapshody.calibration.v1` via a guarded
   localStorage wrapper (`storage.ts`, validates on load), so it survives resizes and bad/old data falls
   back to defaults. Auto-starts once per page load when nothing is saved and tracking is live; the
   Calibrate button reruns it; Esc cancels without saving. A hand not seen during a rerun keeps its
   previous range.

**Consequences:** the zone tints/divider still draw as halves (the zones sit inside them). Changing phase
lengths, percentiles, padding or minimums is tuning; zones crossing the midline or storing pixels would
supersede this.

## ADR-0019: Settings — knob positions persisted, mapped to engine units in pure TS; left-handed mirrors the whole layout

**Context:** task 6.2 — a settings panel with handedness swap and sensitivity sliders (strum threshold,
smoothing, hex size), persisted in localStorage. Earlier ADRs deferred the power-chord octave (0014) and
sound-control persistence (0017) to this task.

**Decision:**
1. **One `Settings` object** (`src/settings.ts`): `leftHanded, strumThreshold, smoothing, hexSize,
   powerOctave, instrument, volume, reverb`, stored as JSON under `strhapshody.settings.v1`. Sliders are
   saved as **0..1 knob positions**, not engine units, and mapped by pure functions, so units can be
   retuned without invalidating saved settings. `validateSettings` merges field-by-field with defaults
   (clamping knobs), so one bad field from an older build never resets the others.
2. **Mappings:** strum threshold → strum detector min crossing speed `2·height·t²` px/s (default 0.3 ≈
   130 px/s on 720 px: above a drifting hand, far below a strum); smoothing → One Euro `min_cutoff`
   exponential 5 Hz → 0.3 Hz (default ≈ 1.4 Hz, ~the old fixed 1.5); hex size → radius scale 0.6–1.0 of
   the largest flower that fits.
3. **Strum threshold lives in the engine** (`StrumDetector.setMinVelocity`): too-slow steps emit nothing
   but still advance the reference point, so a slowly passed line is skipped, never fired late
   (cargo-tested). It's strum-detection logic, so per CLAUDE.md it's Rust, not a TS filter.
4. **Left-handed mirrors everything:** `assignHands({ leftHanded })` swaps the label→role map and the
   screen-side fallback; `calibratedZones(…, leftHanded)` puts the chord zone in the right half; tints,
   zone labels, calibration prompts and the control panel (always on the strum side, so it never covers
   the flower) follow. Calibration now stores `chord`/`strum` boxes plus the handedness they were recorded
   with; switching handedness mirrors them (x → 1−x) instead of discarding them.

**Consequences:** changing a setting re-seeds what it affects (smoothing rebuilds the cursor filters;
handedness resets every per-hand detector). Retuning mapping constants is not an ADR change; storing
engine units or dropping the field-wise merge would supersede this.
